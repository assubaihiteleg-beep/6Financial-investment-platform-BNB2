# خطة إعادة هيكلة البناء ونشر المنصة المالية ضمن حدود الحصة المجانية

تهدف هذه الخطة إلى حل مشكلة تعارض حصة المعالج أثناء النشر (`Request CPU 2000m exceeds limit 1500m`) عبر إعادة هيكلة بناء وتشغيل التطبيق داخل بيئة Google AI Studio Starter Tier، مع الحفاظ الكامل بنسبة 100% على تصميم الواجهات الحالي، الإجراءات، والصلاحيات، وقاعدة بيانات Firestore الحالية.

### User Review & Critical Decisions

> [!IMPORTANT]
> **القرارات المؤكدة من المستخدم في مرحلة التوضيح:**
> 1. **الهدف الرئيسي:** تمكين نشر التطبيق بنجاح من نافذة النشر الرسمية (Publish Modal) ليعمل كرابط عام ومستقل لأي مستخدم وخارج جلسات AI Studio.
> 2. **الموافقة على إعادة هيكلة البناء:** الموافقة على تعديل طريقة البناء والتشغيل بشرط عدم تغيير أي تفصيل في الواجهات الحالية، أو تجربة المستخدم، أو منطق عمل النظام، أو بيانات Firestore الحالية.

---

### 1. Overview & Core Concept

* **المشكلة الحالية:** المنصة مبنية حالياً بنظام حاوية متعددة المراحل (`Dockerfile`) تتطلب خادم Node.js منفصل (`api-server`) وواجهة Vite منفصلة، مما يجعل نظام النشر السحابي (Cloud Run Orchestrator) في AI Studio يطلب افتراضياً حاوية ثقيلة بمواصفات `2000m` CPU، وهو ما يتجاوز الحد المسموح به للمشاريع المجانية في منطقة `europe-west2` وهو `1500m`.
* **الحل المعماري المقترح:** إعادة توجيه عمليات إدارة البيانات (إدارة المستفيدين، الوكلاء، المراحل المخصصة، المعاملات المالية، وسجل التدقيق) لتعمل مباشرة عبر Firebase Firestore Client SDK المربوط مسبقاً بالمشروع (`academic-camera-g01dl` / `ai-studio-6financialinvest-b4e27bbd-da26-4602-9747-b85b6b7096c0`)، ودمج التطبيق كحزمة ويب حديثة أحادية الصفحة (SPA) مخدومة عبر خادم خفيف قياسي متوافق مع نمط AI Studio القياسي، مما يخفض متطلبات النشر السحابي إلى ما دون `1000m` CPU ويسمح بنشر المنصة فوراً.

---

### 2. User Experience & Visual Design

* **تطابق بنسبة 100%:** لن يطرأ أي تغيير على شكل الواجهات أو الألوان أو الخطوط أو توزيع العناصر:
  * **شاشة تسجيل الدخول:** تسجيل دخول المشرف (Admin)، تسجيل دخول الوكيل (Agent)، ودخول المستفيد عبر الرابط المخصص (`/client/:slug`).
  * **لوحة تحكم المشرف:** إدارة المستفيدين، الفلاتر والبحث المتقدم، إدارة الوكلاء وتعيين الصلاحيات الـ 13، نافذة إسناد عدة وكلاء للمستفيد الواحد، إدارة المراحل المخصصة والتجميد/التعديل، وإشعارات الإيداع.
  * **لوحة تحكم الوكيل:** عرض المستفيدين المسندين إليه فقط، تطبيق الصلاحيات الممنوحة له، وإضافة الأرباح أو المستفيدين وفق الحصة المحددة.
  * **بطاقة المستفيد:** عرض البطاقة المتدرجة بالألوان، تفاصيل المراحل، أرقام الآيبان، الأرباح، والرسوم، مع عرض أسماء كافة الوكلاء المسندين إليه فورياً.
  * **المزامنة اللحظية:** تظل تعمل في الوقت الفعلي (`onSnapshot`) عبر Firestore عبر جميع الأجهزة والمتصفحات.

---

### 3. Key Product Decisions & Trade-Offs

* **القرار الأول: معالجة البيانات عبر Firestore مباشرة بدلاً من خادم الوسيط المزدوج**
  * *الخيار المعتمد:* نقل دوال الإنشاء والتعديل والحذف لتتعامل مباشرة مع مجموعات Firestore (`beneficiaries`, `agents`, `custom_phases`, `financial_transactions`, `notifications`, `audit_logs`).
  * *السبب:* يلغي الحاجة إلى حاوية Cloud Run ضخمة بطلب معالج 2 vCPU، ويوحد مصدر الحقيقة للبيانات في Firestore مباشرة مما يمنع أي تباين بين Drizzle وFirestore.
  * *البديل المستبعد:* محاولة إجبار Cloud Run على قبول 2000m دون ترقية مدفوعة، وهو أمر مستحيل تقنياً بسبب قيود الحصص المفروضة على المنطقة في الحساب المجاني.

* **القرار الثاني: الحفاظ على نفس قاعدة البيانات ومعرف المشروع**
  * *الخيار المعتمد:* استخدام نفس الإعدادات الموجودة في `firebase-applet-config.json` بنفس الـ Database ID دون إنشاء أي مشروع جديد أو حذف أي بيانات سابقة.
  * *السبب:* التزام تام بشروط المستخدم الصارمة بعدم نقل البيانات أو تفعيل الفوترة.

#### خطوات التنفيذ البرمجية المحددة:
1. **تحديث طبقة البيانات في الواجهة:**
   * تحويل دوال `apiFetch` الخاصة بالمستفيدين والوكلاء والمراحل إلى دوال Firestore مباشرة (`addDoc`, `updateDoc`, `deleteDoc`, `getDocs`, `onSnapshot`).
2. **تبسيط تكوين البناء والتشغيل:**
   * توحيد ملف البناء `package.json` الرئيسي ليعتمد البناء القياسي الخفيف المتوافق مع AI Studio دون استدعاء حاويات Cloud Run الثقيلة.
3. **الاختبار والتحقق:**
   * التحقق من سلامة البناء عبر `compile_applet` واجتياز الفحص البرمجي بدون أخطاء.
   * التأكد من فتح المنصة بشكل كامل ومستقل للمستخدمين على الرابط العام.
